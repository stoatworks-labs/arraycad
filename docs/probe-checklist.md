# ArrayCalc probe — what to do and what to look for

Generated by `scripts/make_probe_venue.py`. Two files:

- **`arraycad-probe-A.dbacv`** — safe. Only constructs observed in a real ArrayCalc
  12.8.2 export. This one should open.
- **`arraycad-probe-B.dbacv`** — adventurous. Untested constructs. May be rejected, and
  that is itself an answer.

Do A first. If A fails there is no point in B.

---

## The procedure

1. Open the file in ArrayCalc.
2. **If it refuses to open, stop and say what the error said.** That is the single most
   valuable result and it does not need anything else.
3. Look at the venue in plan and in 3D.
4. Answer the questions below — most just need a glance.
5. **Save, then export the venue back out**, without changing anything you don't have to.
6. Send the exported file back.

The export is the real prize: comparing it against what went in shows what ArrayCalc
silently corrected, which is where the remaining wrong assumptions are.

## File A — questions

Every object's name says what it is testing.

### The big one: what does ArrayCalc call each plane type?

Objects **A10, A11, A12, A13** are identical quads that differ only in `PlaneType`
(1, 2, 4, 5). Open each one's properties and note **the exact wording ArrayCalc uses**.

| Object | PlaneType | This project currently calls it | ArrayCalc actually calls it |
|---|---|---|---|
| A10 | 1 | Audience | ? |
| A11 | 2 | Surface | ? |
| A12 | 4 | Stage | ? |
| A13 | 5 | Soundscape | ? |

Also worth noting: does the type dropdown list any option this project has never seen?
`PlaneType 3` was never present in the sample and its meaning is unknown.

### Geometry

| Object | What it should look like |
|---|---|
| A01 | Flat 4 × 3 m rectangle |
| A02 | Same rectangle, **raked** — the far-X edge 0.6 m higher. Confirms a quad need not be planar |
| A03 | Triangle |
| A04 | A solid box 4 × 3 × 1.5 m — **not** six separate planes |
| A05 | A curved ring segment, inner radius 10 m, outer 14 m, 45° sweep, **rising 1 m from inner to outer**. If it comes out flat, `InnerZ`/`OuterZ` do not rake it |
| A06 | A 6 m bar pointing **north-east** in plan (45°), not along X |

### Listener height — derived or independent?

- **A20** is an Audience object written with `ListenerHeight 0.77`.
- **A21** is a Surface object written with `ListenerHeight 1.55`.

Does ArrayCalc keep those numbers, or reset them to 1.2 / 0.01? Check in the UI, and it
will show in the re-export either way.

### Groups

**A30** is a group whose own origin is `(0, -8, 0)`, containing two children placed at
local `(2, 0)` and `(2, -4)`.

If group transforms compose, the children sit at world **(2, -8)** and **(2, -12)**.
If the group origin is ignored, they sit at (2, 0) and (2, -4). Their names say where they
should be.

### Numbers

**A22** has one corner at `x = 4.0000000000000009`. If that comes back as `4` or
`4.000000000000001`, this project's number formatting is not what ArrayCalc uses.

## What the returned export will settle

Even without answering a single question by eye, the exported file resolves:

- whether `ParentVenueObjectId` really is depth-first document order (if ArrayCalc
  renumbers, the new numbers show the true scheme)
- whether the `%.17g` number formatting is right
- whether attribute order matters
- whether `ListenerHeight` is derived from `PlaneType`
- what ArrayCalc does to a group transform it did not write itself
- whether any object was dropped, merged, split or re-shaped

If ArrayCalc changes something, the diff says exactly what.
